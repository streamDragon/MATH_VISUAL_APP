# משימה לסוכן עם גישה לחשבונות — הפעלת השירות המשותף

אפשר להעתיק את המסמך הזה לסוכן עם גישה לדפדפן ולמחשב של חגי.

## מצב הקוד

התרגול החינמי פועל ללא חשבון וללא AI. מסכי בקשות, מנויים וקבוצות מחוברים ללקוח Supabase, אבל מיגרציית השירות החדש **לא הופעלה בחשבון החי בתהליך הבנייה הזה**. נבדקה מקומית על PostgreSQL באמצעות PGlite. אין לטעון ששאלה נשלחה, שקבוצות פועלות או שגבייה הופעלה לפני בדיקת השרת בפועל.

## הוראות לסוכן

1. פתח את הפרויקט `streamDragon/MATH_VISUAL_APP`, משוך את הגרסה האחרונה ובדוק את מצב הענף לפני שינוי. שמור עבודה קיימת.
2. הרץ `npm ci`, `npm test`, `npm run test:import`, `npm run build`.
3. היכנס לחשבון Supabase של בעל הפרויקט. הלקוח משתמש כעת בפרויקט `qaxuqliefevglwtntmmw`. ודא שזה הפרויקט הרצוי באמצעות בעל החשבון וההגדרות הקיימות. אל תציג מפתחות סודיים ואל תכניס `service_role` לקוד דפדפן.
4. בדוק אם קיימות טבלאות `learning_*`. אם המיגרציה כבר הוחלה, אל תריץ שוב את פקודות היצירה. אם אין סכימה חדשה, הפעל כ־project owner את `supabase/migrations/202610040001_learning.sql` ואז את `supabase/seeds/learning-bank.sql`. המיגרציה בתוך transaction וכוללת RLS ואחסון תמונות פרטי.
5. הגדר ב־Auth את כתובת האתר ואת redirect URLs המורשים: `/learn.html` ו־`/review.html` בדומיין הפרסום. בדוק מסירת קישור כניסה באימייל ו־SMTP בהתאם למצב החשבון.
6. בקש מחגי להיכנס פעם אחת. אמת את המשתמש הנכון ב־Auth Users ורק אז הוסף את ה־UUID שלו ל־`public.learning_moderators`. אל תעניק ניהול לכל משתמש ואינך רשאי לנחש UUID.
7. בדוק בחשבון תלמיד א׳: שליחת טקסט ותמונה, קבלת מזהה אמיתי, קריאת הבקשה לאחר רענון. בחשבון תלמיד ב׳: אין יכולת לקרוא את הבקשה או התמונה של א׳. בדוק שמשתמש רגיל אינו יכול לפרסם, לערוך מנוי או להעניק לעצמו נקודות דרך כתיבה ישירה לטבלאות.
8. ב־`review.html`, בדוק שחגי רואה את התור. העתק משימה לצ׳אט שלו, הכן JSON לפי `content/learning-bank.json`, אמת מתמטיקה ותיווך, ופרסם. מענה לבקשה צריך להפנות להמחשה חינמית כדי שהמבקש יוכל לפתוח אותה.
9. צור מנוי ניסיון למורה ב־`learning_entitlements` מתוך מסוף הבעלים, לא דרך הדפדפן של תלמיד. צור כיתה ובחר משימות. חבר תלמידים בקוד, ובדוק את המפה משני מכשירים. בקבוצת solo בדוק עד 11 משתתפים, טווח שליטה המבוסס על השלמות וכינויים בלבד. אין להמציא משתתפים.
10. בדוק השלמה נכונה ושגויה, השלמה חוזרת ובונוס פסגה: 40 נקודות לכל פעילות פעם אחת; 20 נקודות לראשון שמסיים את מסלול הקבוצה. זו תחרות לימודית קלה, לא מערכת למבחן מאובטח: התשובות לתוכן החינמי נמצאות בקוד המקומי.

## תשלומים — שלב נפרד

מסכי המסלולים קיימים; אין checkout או חיוב פעיל. אין לשנות הרשאות לפי הצלחה שהלקוח מדווח. לאחר בחירת ספק תשלומים מתוך החשבון של הבעלים: הוסף checkout בצד שרת, webhook עם אימות חתימה ואירוע ייחודי, הענקת/ביטול entitlement לפי אירוע מאומת ובדיקות sandbox של חידוש, ביטול וכשל. רק אחר כך פרסם מחירים והפעל חיוב אמיתי. לא צורפו פרטי ספק או חשבון סליקה בבקשה המקורית.

הבנק הראשוני מקורִי והוא ציבורי ב־GitHub לצורך פיילוט. RLS מגביל גישה לתוכן המורחב דרך האפליקציה, אך אינו הופך תוכן שנמצא במאגר ציבורי לסודי. תוכן עתידי בתשלום יש לכתוב ולשמור במערכת ניהול/מאגר פרטי ולא לפרסם ב־GitHub הציבורי.

## ייבוא ספרים ואתרים

אין סריקה אוטומטית של טיק־טק או העתקת ספר שלא סופק. הכלי `scripts/import-question-candidates.py` מקבל קובץ שסופק כחוק ושומר טיוטות עם מקור ומספר עמוד. לדוגמה:

```bash
python3 -m pip install -r scripts/requirements-import.txt
python3 scripts/import-question-candidates.py supplied.pdf --source "שם הספר והמהדורה" --permission-note "חומר מקורי של חגי" --grade 9 --language he --output local-drafts.json
```

אפשר להזין TXT, Markdown, HTML שנשמר מאתר, DOCX או PDF עם שכבת טקסט. PDF מצולם דורש OCR ותיקון אנושי. פיצול שאלות הוא heuristic; נוסחאות וגבולות שאלה מחייבים בדיקה. קובץ הטיוטות אינו קובץ פעילות לפרסום. עבור כל טיוטה יוצרים פעילות דו־לשונית עם ניבוי, המחשה, תיווך ושאלת העברה, ואז מאמתים ב־`review.html`.
